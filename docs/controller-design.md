# task-router 独立调度与主模型恢复设计

日期：2026-09-14。本文是下一阶段设计，不代表已经实现或通过恢复测试。

后续进展：已完成使用明确任务类型的独立命令行原型，支持持久化、受管执行、
有界重试和任务级续做，见 [原型说明](controller-prototype.md)。下文完整架构中的
自动分类、常驻服务和插件入口等仍属于后续设计。

## 1. 推荐方向

保留现有插件作为安装与工作流入口，增加一个独立于模型回合的 controller。
由 controller 接收并保存任务，调用 GLM 进行语义分类，校验分类结果，选择
角色模型池，启动实际执行，并管理状态、预算、取消及恢复。

GLM 不再承担必须持续在线的总控制者角色，而是 controller 可以替换的分类/
规划模型。普通讨论、代码工作和最终文字整理同样作为有状态的模型任务运行。
模型失效时，程序仍然能够判断下一步并输出任务状态。

现有 router_core.py 的严格校验与候选选择可以复用。原生 spawn_agent 是当前
模型回合的工具，不是假定 Python 后台进程可以直接调用的 API。controller
需要一个独立、经验证的 Codex 执行适配器。

## 2. 覆盖范围取决于入口

| 接入方式 | 能覆盖的问题 | 剩余边界 |
|---|---|---|
| 只增强 skill | 改善主模型遵循规则的概率 | 模型仍可能不调用路由；主模型失效时逻辑无法运行 |
| 插件通过 MCP 提交到 controller | 已提交任务的调度、重试和状态独立于前台模型 | 提交之前主模型失效，controller 不知道用户这条请求；原线程也可能无法汇报结果 |
| 用户任务先进入 controller，再启动模型 | 任务从接收到完成都由程序持有，可管理分类模型和 worker 的故障 | 需要一个受 controller 管理的入口，不能仅安装 skill 就透明接管全部原有线程 |

如果要同时解决“依赖主 agent”和“主模型失效”，应以第三种为目标。第一版
可以提供本地 CLI 入口，之后复用同一 controller 增加 MCP 或其他前端。
MCP 是入口适配方式，本身不提供强制路由或独立持久化保障。

## 3. 执行适配器选择与证据

本机 codex-cli 版本为 0.154.0。2026-09-14 的官方 app-server 页面请求仍返回
HTTP 403，因此核对了该 CLI 自身导出的 JSON Schema，而不是依赖未打开的文档。

执行 `codex app-server generate-json-schema --out <临时目录>` 后，确认：

| 本机协议能力 | Schema 中可见的字段 | controller 用途 |
|---|---|---|
| thread/start | model、modelProvider、cwd、sandbox、approvalPolicy | 为受管任务建立明确的执行会话 |
| turn/start | threadId、input、model、effort | 显式选择本轮模型和推理档位；覆盖也影响后续轮次 |
| turn/interrupt | threadId、turnId | 请求中断指定执行轮次 |
| thread/resume | threadId、model、modelProvider 等 | 恢复已保存的受管会话并指定模型 |
| turn/completed | turn.status、turn.error | 收集最终状态，而不是仅匹配输出文字 |
| error | threadId、turnId、error、willRetry | 区分内部仍在重试和需要 controller 处理的失败 |
| TurnError | 可选 codexErrorInfo、部分变体中的 httpStatusCode | 获取比自由文本更可靠的失败类别 |

这些是接口定义证据，尚未实测通过 app-server 的模型切换、会话恢复、中断
后的进程退出及权限交互。CLI 将 app-server 标记为 experimental，必须做版本
兼容检查并把协议操作封装在单独适配器中。

推荐先对 app-server 做小型可行性实验，再将其作为主要适配器。它的结构化
事件和中断接口比解析终端文字更适合管理会话。优先启动 controller 自己拥有
的 stdio app-server，不去接管或杀掉用户正在使用的共享 daemon。

`codex exec --json --model ...` 与 `codex exec resume --model ...` 的帮助也已
确认存在。若 app-server 原型有阻碍，可先用 exec 实现受管 CLI 任务，但要
单独验证取消、会话恢复与权限边界；不要为了赶进度关闭 sandbox/审批策略。

## 4. 核心组成

- 入口：任务提交、状态查询、取消和续做。请求获得稳定 task_id，后续操作
  使用该 ID；客户端重复提交同一请求键时返回已有任务。
- 策略解析器：复用 v0.4 的 profile/role 选择，增加可用性及预算筛选。冻结
  每个任务的配置摘要，避免进行中任务因配置修改换用另一套规则。
- 状态库：Python 标准库 SQLite，保存任务、执行尝试、事件、检查点和冷却。
  日志保留有限内容；不保存 API key 或未经清理的供应商错误正文。
- 执行适配器：创建/恢复受管会话、启动/中断 turn、收集事件、转发权限请求。
- controller 主循环：根据状态执行下一步，不依赖模型输出一句“请重试”。
- 可恢复的进程管理：持久化任务意图，controller 重启后核对活跃任务。后续
  可由 systemd --user 等管理 controller 生命周期，而不是假设程序永不崩溃。

第一版不要求额外的常驻网络端口、Web 页面或消息队列。Python asyncio、SQLite
和受管 stdio 进程已足够验证关键路径；有明确多客户端需求后再增加本地服务入口。

## 5. 任务执行过程

1. 先保存用户原始目标、已有授权边界、工作目录和配置摘要，再开始调用模型。
2. 有明确任务类型时直接使用；不明确时调用只读 GLM 分类/规划任务。
3. 分类结果必须符合限定的任务/角色结构。计划不能把“只讨论”扩大成允许修改，
   也不能自己发明工具、越过文件范围或扩大权限。结果错误可以有限重试，仍不
   清楚则请求澄清；未知类型不能自动进入写入模式。
4. 程序选择兼容模型，并在调用前持久化执行意图和尝试次数。
5. 启动 worker，传入任务包及权限约束，持续接收执行事件。worker 不拥有
   任意扩大候选池或重置预算的权力。
6. 根据真实产物和验收结果判断完成；检查失败进入定向修正流程，服务错误
   进入可用性恢复流程。普通测试失败不应该把模型标记为服务不可用。
7. 先保存结果再通知前端。文字汇总模型失败时可以展示已有结果，不重新运行
   已经完成的代码修改任务。

保留一个很小的状态集合：queued、classifying、running、waiting_for_user、
recovering、succeeded、failed、cancelled、unknown。执行尝试单独记录阶段，
避免分类完成、代码完成和最终汇总混在同一个成功标记里。

## 6. 主模型失败如何恢复

分类/规划 GLM 也使用模型池，例如 glm-5.3-flash 优先，glm-5.3 为候选备份。
具体档位及候选顺序复用已验证配置，不把模型名字相近当作拥有独立额度的证明。

如果 GLM 在分类阶段发生可恢复的服务错误：controller 仍持有用户请求，记录
失败，在总预算内选择备份分类模型；得到有效分类后继续启动 worker。分类
模型与 worker 的生命周期分开，分类模型失败不会销毁已经完成的 worker 结果。

如果某个 worker 模型失败：先判断该 turn 是否仍在内部重试。willRetry=true
时不能立即再派一个 writer；仍需遵守任务总体时间预算，必要时请求中断。
只有确认进入可处理的终态或核对执行状态后，才选择备用模型。

在同一受管会话内恢复失败时，可尝试 thread/resume 或下一轮显式 model 覆盖。
如果目标模型不能兼容原来的工具历史、上下文或 provider 状态，则新建受管
会话，传入目标、已确认决定、当前 diff、测试结果和剩余工作。这是任务层续做，
不是承诺跨模型保留所有隐藏状态。

处理依据：明确的鉴权/配置错误先报告；503 视为服务错误而非直接认定额度
耗尽；429 根据已获取的信息区分限流与额度问题；全部独立候选不可用时有界
停止。网络错误本身可能同时影响多个型号，不能无限轮询同一供应商。

## 7. 防止重复执行

状态落盘和模型/工具执行之间没有天然的跨进程原子事务。即使有 task_id，
也不能承诺所有外部操作严格只执行一次。

- 每个工作区首版只允许一个活动 writer。取消请求发出、心跳超时、锁租约
  过期都不等于旧 writer 已停止，不能仅据此开启第二个 writer。
- 启动请求已发出但确认消息丢失时，标记 unknown，查询受管 thread/turn 的
  实际状态；不能直接重发启动请求并假设服务器会自动去重。
- 收到中断确认后仍要核对工具进程和已产生的副作用。无法确认时保留未知
  状态并明确报告，不假装恢复已经完成。
- 代码重试先检查实际 diff、测试产物和已执行步骤，发送“完成剩余工作”的
  任务包。不能只靠 git HEAD 判断状态，也不能清除用户已有的未提交修改。
- 发布、推送和其他外部写入使用服务支持的幂等键/结果查询，或保留为需要
  核实的步骤，不能因为模型换了就自动重放。原来的授权边界始终有效。
- 进程崩溃后先核对受管 server 和任务状态，再恢复调度。SQLite 记录成功
  不代表外部执行必然成功，未记录成功也不代表操作没有发生。

## 8. 预算、权限和观察

总尝试次数在调用前由程序计数，不能让分类模型或 worker 自己填入新的计数。
首版可采用每阶段小额限制加任务总上限，质量修正和分类失败均计入总体预算。
预算耗尽、用户取消及权限等待是不同状态，不通过换模型绕过。

worker 不应拥有自由修改 controller 状态和策略文件的权限；进程范围由执行
适配器按任务授权设置。若宿主无法隔离所需权限，要报告该限制，不能用提示词
代替强制权限边界。执行器需要将权限请求转发给用户或已有授权机制，不能
默认同意所有请求。

记录 task_id、attempt_id、thread_id、turn_id、配置摘要、请求模型/档位、
错误类别、取消状态及验证证据。实际返回模型与 token 用量仅在接口提供时记录，
未知费用和余额保持未知。向用户显示失败后切换了哪个模型以及哪些步骤已经完成。

## 9. 实施顺序与验收

| 阶段 | 交付 | 验收重点 |
|---|---|---|
| 可行性原型 | 受管 app-server 初始化、启动只读任务、事件接收、中断、指定另一模型恢复 | 当前 provider/认证可用；协议事件可关联；不干扰现有线程；中断边界可说明 |
| 独立调度核心 | SQLite、任务入口、分类 worker、角色池、状态和总预算 | 不依赖模型主动调用重试；重复提交不会重复创建任务；无候选明确停止 |
| 恢复路径 | 主分类模型失败、worker 失败、断线及 controller 重启处理 | 错误分类有界；旧 writer 未终止时不派新 writer；保留部分产物 |
| 插件接入 | MCP/命令入口、状态查询、错误提示和升级安装 | 已提交任务不依赖前台模型存活；清楚说明未提交请求的覆盖边界 |

优先测试：分类模型在首个响应前失败、Codex 内部仍重试、写了一半后断线、
完成事件已保存但前端没收到、启动请求后断线、用户取消、等待权限时超时、
controller 重启、全部候选失败。使用假事件做确定性状态测试，再用有限真实
任务验证执行接口；假事件测试不等于真实 503 恢复实测。

第一项交付应是可行性原型及证据。确认实际接口和恢复行为后，再确定常驻服务
与前端接入方式，避免先写完整调度服务却发现入口无法控制目标会话。
