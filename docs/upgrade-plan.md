# task-router 多模型升级方案与风险评审

日期：2026-09-14。基线：发布仓库 v0.3.0。

后续进展：v0.4 已实现 A/B 的配置、角色池与安装基础，真实验证及未完成项见
[v0.4 验证记录](v0.4-validation.md)。下文保留原始评审和后续设计，不代表所有阶段均已实现。

本文是设计与验收方案。仅新增本文档，未修改路由配置、安装器、Codex 主模型或已安装插件。下文新增命令、字段和运行机制均为拟实现内容。

## 1. 目标与结论

保留用户确定的分工：GLM 主 agent 负责调度，GPT 子 agent 负责讨论与方案，GLM 子 agent 负责代码阅读、修改和验证。用户对某次任务的明确模型选择优先于默认策略。

下一版首先把现有插件做成可验证、可恢复、可维护的任务调度工具，然后扩充模型。建议的执行链为：

任务及当前工作状态 -> 角色 -> 兼容候选 -> 健康状态过滤 -> 按优先级选择 -> 委托执行 -> 验收和状态记录。

主模型仍负责理解任务、传递上下文、维护工作进度及向用户汇报。主模型不能只做字符串分类后转发，也不能假设它的消耗可以忽略。脚本负责可确定的配置校验、候选筛选、预算和状态管理。

本阶段不加入代理层。插件不会拦截主模型请求，无法保证主模型失效时自动恢复；也不能保证主模型每次都会调用 skill。持久化状态脚本只有在宿主调用它时才能记录实际结果。

## 2. 当前事实与证据边界

- 本机 `~/.codex/codex-models.json` 有 25 个模型条目，其中 6 个 GLM。模型目录条目不是逐模型连通性、额度或工具调用能力的测试证明。
- 插件 `routing.json` 只登记 5 个模型，即 2 个 GLM 和 3 个 GPT。不能把先前结果汇报为“完成 6 个 GLM 的实际路由验证”。
- 本机 Codex 默认模型为 `gpt-6-astra`，插件预期主模型为 `glm-5.3-flash`。配置文件中的预期值不会切换当前线程模型，读取默认配置也不能证明现有线程正在用哪个模型。
- 本轮 `spawn_agent` 工具说明只明确列出 5 个可覆盖模型，未列出目标 GLM 和较新的 GPT。这是需要核实的兼容性差异，不据此断言其永久不可用，也不绕过当前运行环境的限制。
- 本机模型目录中存在统一填写的描述和上下文长度，不能把这些字段当成上游保证。插件中先前填写的能力标签同样不是测评结论。
- 已有证据包括查表命令、结构校验、历史上的一个 GLM 最小回复任务和本机安装过程；缺少新模型实际工具任务、可控故障恢复及跨环境安装的验证。
- 上轮官方文档读取返回 HTTP 403。本方案依据本地实现及当前工具声明，不依赖未经确认的产品能力。

## 3. 需要优先解决的问题

P1 表示优先于扩充自动路由；P2 表示基础路径跑通后处理。以下区分本轮复现的问题和通过代码检查发现的风险。

| 优先级 | 问题与证据 | 可能后果 | 处理方式 |
|---|---|---|---|
| P1 | `install.sh:22` 先删除目标目录，再复制插件 | 个人路由配置丢失；复制失败后旧版本也不在原位 | 配置独立存放；分阶段安装；保存可恢复的旧版本 |
| P1 | `route.py:29` 把 `delegate` 强制转成布尔值；已复现字符串 `"false"` 变成 `true` | 本想本地处理，却发起委托 | 严格类型校验，错误必须指出字段路径 |
| P1 | `route.py:32` 只在提供模型时检查；已复现 `delegate: true` 返回 `model: null` | 委托可能继承主模型或报错，分工失效 | 委托必须解析出有效目标；空池也必须明确报错 |
| P1 | `route.py:42` 只查替补名单；已复现自身、重复项被保留，未知项被静默删除 | 无效重试、意外遗漏备份，难以诊断 | 校验候选唯一性、引用完整性及重试上限 |
| P1 | `SKILL.md:70` 默认继承完整上下文，没有 worker 防递归约定 | 子 agent 再次委托；讨论上下文挤占输入额度 | 明确 dispatcher/worker 角色；最小必要任务包；最大委托深度 |
| P1 | `SKILL.md:87` 按错误文本判断失败，重试前没有确认旧任务停止 | 已修改一半的任务重复执行；多个 agent 同时写文件 | 任务状态跟踪、确认终止、检查现有产物后续做 |
| P1 | 无目录与运行时委托能力的交叉检查；推理强度默认继承 | 选到不能委托的模型，或因参数不兼容失败 | 能力预检；显式解析目标模型支持的参数 |
| P2 | `cooldown_seconds` 和 `on_status` 没有执行逻辑；skill 按整个会话排除失败模型 | 冷却无效，临时故障在长线程内变成永久禁用 | 持久化失败分类、作用域和恢复时间 |
| P2 | `SKILL.md:3` 的发现描述偏代码任务；“继续”与任务延续没有明确约定 | 纯讨论可能不加载路由；短指令丢失原任务 | 覆盖讨论场景；按未完成任务理解续接指令 |
| P2 | `small-edit` 仍留在主线程；`long-context` 混合长度和任务类型 | 用户期望的 GLM 编码分工被绕开；分类重叠 | 所有代码编辑进入编码角色；长度作为筛选条件 |
| P2 | 配置相对已安装 skill 读取，安装时复制到缓存 | 修改源码配置不一定影响当前安装；更新后用户误以为规则已生效 | 显示配置实际来源、摘要和版本；支持外部完整配置 |
| P2 | 发布仓库、开发副本、安装缓存有多个位置 | 修改漏同步，测试与发布内容不一致 | 仓库作为唯一维护源；开发副本和缓存作为派生产物 |

其他本轮复现：配置根节点为数组时直接出现 `AttributeError`；同时给位置参数和 `--task` 时静默采用后者。应统一成清楚的配置或命令行错误。上述都是本地测试，没有发送模型请求。

## 4. 模型与角色的配置设计

### 4.1 使用角色池

| 角色 | 范围 | 初始候选，仅用于测试安排 |
|---|---|---|
| dispatcher | 理解、分类、派发、状态维护、汇报 | `glm-5.3-flash` |
| discussion | 普通技术问答、解释与方案讨论 | `gpt-5.4`、`gpt-5.5` |
| reasoning | 复杂方案权衡、困难分析 | `gpt-5.6-sol`、`gpt-6-astra` |
| coding | 代码阅读、实现、重构、测试 | `glm-5.3`、`glm-5.2` |
| coding-light | 有边界的检索、简单机械修改 | `glm-5.3-flash`、`glm-5-turbo` |
| review | 依据真实 diff 和测试结果独立审查 | 先从通过测试的 GPT 池中选取 |

型号顺序是待验证的配置偏好，不是性能排名。其余模型保持未启用，逐个通过任务测试后再加入。音频、实时模型暂不进入文本编码池；用途和额度来源未知的 `gpt-reserve` 保持未验证状态。

### 4.2 分离稳定的名称和实际模型 ID

任务引用角色，角色引用本地 profile，profile 存放实际 `model_id`。例如角色使用 `discussion-main`，实际模型从 `gpt-5.4` 换成另一型号时，只改该 profile。这样无需在任务表、模型目录和替补链里反复替换同一个 ID。

建议 v2 配置包含：

- `schema_version`：严格校验和迁移依据。
- `dispatcher`：期望主模型及故障时的行为说明。只做核对，不能伪装成自动切换线程的接口。
- `profiles`：模型 ID、启用状态、供应商标识、已确认的别名或额度组、参数配置。
- `roles`：有序 profile 列表；跨角色兜底使用显式配置。
- `tasks`：任务类型到角色的映射，以及读写范围、复杂度等约束。
- `retry_policy`：总尝试次数、总体时间预算、冷却规则和耗尽处理。
- `limits`：委托深度、写入并发、日志保留等运行限制。

能力和可用性探测结果属于状态，不回写为用户配置。目录声明、供应商说明、实际测试分别保留来源和时间；未知值不能被当成无限上下文、零成本或可用。

### 4.3 候选选择规则

先检查用户指定的目标和任务授权，再依次筛选：是否启用、当前会话是否支持委托、所需工具和输入类型是否兼容、上下文和输出空间是否够用、目标推理参数是否有效、是否处于冷却期、当前任务是否已经尝试过。最后按角色配置的优先级选择。

一个任务耗尽候选后，不递归展开每个模型的另一条替补链。跨家族兜底在角色层显式配置，总重试预算不因换角色而重置。

模型名相似不能证明它们共享或独立拥有额度。仅在供应商信息明确时配置别名与额度组。也不能因为某个模型返回一次 503，就封禁整个供应商。

首版保持确定性的优先级列表。没有可靠的价格、剩余额度和质量数据前，不实现自动学习的评分器或宣称按剩余额度调度。

## 5. 委托与上下文协议

### 5.1 调度员与执行者分工

调度员只读取定位和交接所必需的信息。大范围读代码交给编码 worker，避免主线程先把全部工作做一遍。模型输出是待验收结果，主线程保留事实核查和错误修正职责。

worker 任务消息明确标记 `execution_role: worker`、任务 ID 和委托深度，要求直接执行分配任务，不再激活调度流程。默认深度为 1。单靠提示词不能严格保证这一点：如果运行时不能禁用 worker 的派生工具，就保留为约定，并检测观察到的额外委托、记录实际覆盖边界。

讨论和审查默认只读；授权的编辑任务才允许更改规定范围。方案讨论不自动转成实施。对“继续”“按刚才的改”使用已有任务和上下文判断，不能仅凭句子短就归类为闲聊。

### 5.2 任务包与结果包

任务包至少携带：原始目标、用户已确认的约束、相关决定、必要文件或参考位置、允许读写的范围、验收条件、已有任务状态和输出格式。新 worker 不依赖它无法访问的绝对路径或私有主线程状态。

结果包至少携带：任务状态、结论和证据、改动文件、执行过的验证及结果、未解决事项。讨论 worker 不应被要求提交“改动文件”作为唯一完成标准。没有运行测试必须写明，不能仅回一句成功。

优先使用最小必要上下文；讨论连续性可通过复用仍可用的 worker 或携带结构化摘要维护，不能假设跨轮、跨线程子 agent 一定持久存在。仅在需要且目标模型容纳得下时使用完整 fork，并为工具定义、输出和后续交互保留空间。

### 5.3 文件与执行状态

先通过隔离工作区的小实验确认本机子 agent 的文件共享或分叉行为，不从 `fork_context` 推断文件系统语义。首版每个工作区只允许一个活动写入 worker；只读任务可在明确范围内并行。

状态建议为 `planned -> running -> succeeded / failed / cancelled / unknown`。等待超时只说明状态未知，不等于任务结束。未知状态先查询或停止原 worker；无法确认停止时，不并发启动替代写入任务。

模型失败可能发生在修改之后。重试前查看当前 diff、检查已执行步骤，给新 worker 一份续做任务包。推送、部署、提交外部请求等有副作用操作不能因换模型盲目重放；原有授权边界始终有效。

## 6. 故障恢复与状态管理

| 类型 | 判断依据 | 建议处理 |
|---|---|---|
| 无效模型、参数或接口不兼容 | 结构化错误及调用阶段 | 标记配置或能力问题；不反复重试相同参数 |
| 401/403 | 鉴权或授权错误 | 报告对应凭据引用/权限问题；避免整池轮询 |
| 429 | 限流，或错误体明确说明的额度问题 | 优先采用可获取的 `Retry-After`；区分请求限流与额度耗尽 |
| 502/503、网络暂时故障 | 服务错误或连接失败 | 有界冷却；在总预算内选择另一兼容候选 |
| 明确额度耗尽 | 供应商结构化错误或可核实说明 | 暂停已确认的额度组；使用独立的备份来源 |
| 上下文过长 | 输入限制错误 | 精简任务包或选更大上下文；不复用原样超长输入 |
| 测试失败、答案不合要求 | 实际产物与验收结果 | 做定向修正或质量升级；不记为服务不可用 |
| 等待超时、状态不明 | agent 未返回终态 | 核实运行状态与副作用；不能直接判定没额度 |

宿主有时只能收到错误摘要，无法取得 HTTP 头或状态码。此时保留原始错误类别为未知，依据有限证据保守处理；不宣称错误分类总是准确。

建议起始限制：一个子任务最多 3 次实际模型执行尝试，质量修正也计入；总体时间预算按任务类别配置。冷却使用有上限的退避，能读取 `Retry-After` 时优先参考。达到预算后给出明确状态和已完成部分，不静默交给主模型无限继续；用户明确续做才建立新的尝试预算。

执行尝试与冷却状态使用 Python 标准库 SQLite，便于多个会话通过短事务更新。键包含 provider、model/profile、工作区或任务作用域；确认共享额度时另有额度组键。容量和网络故障与任务质量问题使用不同记录，避免一个代码错误让其他线程误判模型离线。

冷却到期不代表恢复成功，应允许一个受控探测任务；多个线程不能同时争抢探测。取消、进程崩溃后的遗留任务先标成待核实，不通过计时自动认定外部操作已撤销。

## 7. 配置、安装与分享

建议使用以下位置，支持 XDG 目录覆盖：

- 插件包：默认配置、skill、脚本和文档，随版本升级。
- `~/.config/task-router/routing.json`：完整的用户配置，升级不覆盖。
- `~/.local/state/task-router/state.sqlite3`：本机状态，不能打包分享。

加载优先级为显式 `--config`、环境变量指定路径、用户配置、包内默认配置。每次选择一个完整配置文件；首版不引入隐式深度合并或项目配置。显式指定的文件不存在、损坏或版本不支持时清楚报错，不能悄悄回退到另一套策略。

拟新增的工具入口：`doctor` 检查依赖、配置和当前能力来源；`config init` 生成可编辑配置；`route --explain` 输出选择与跳过原因；`status` 查看故障和冷却；`record-result` 记录宿主报告的结果。现有 `--task`、`--list`、`--failover` 应明确保留或提供迁移说明，不能静默改变含义。

shell 脚本无法直接读取模型回合里的工具定义。运行时能力快照需要宿主提供或使用将来经验证的正式接口，并标明来源和时效。离线 `doctor` 只能报告本地配置兼容性，不能声称已经验证当前 agent 能委托全部目录模型。

安装顺序调整为：检查 Python/Codex 插件命令 -> 校验源包和旧配置 -> 备份并迁移个人配置 -> 在临时位置准备新版本 -> 调用正式 marketplace/安装机制 -> 验证安装结果。失败时保留可恢复副本并报告状态，不删除不相关插件，不擅自改主模型和密钥配置。

发布仓库作为唯一修改源；缓存不直接编辑。新安装读取稳定版本，开发重装沿用 cachebuster 流程。安装器需显示真实配置来源和已安装版本。`--explain` 输出配置摘要，方便确认外部配置变更已被新任务读取；进行中的任务固定使用原配置摘要，避免半途改变兜底顺序。

分享包只包含默认值和说明，不包含 API key、环境变量值、本机状态或私有路径。安装不应替使用者继承作者的供应商凭据。先声明支持的平台，再测试 Linux/macOS；若未实现 Windows 安装器，明确要求 WSL，不能宣称 Bash 安装器原生跨平台。

## 8. 日志与测评

每个执行任务记录：任务 ID、角色、配置摘要、预期模型、调用工具时显式指定的模型、若可取得的实际返回模型、选择原因、尝试序号、耗时、退出类别、验收结果，以及可取得的 token 用量。供应商别名可能影响实际返回值，不以模型自述作为实际路由证明。

默认不记录密钥、鉴权头、完整提示词、完整代码及未经清理的错误响应。缺失的成本或用量标记未知；没有余额接口就不显示剩余额度。设置有限保留时间和大小。

比较对象应包含：单 GLM 完成任务、当前路由方式、候选池路由方式。使用相同任务和验收条件，观察完成率、路由遵循率、质量、总耗时、重试次数、总用量。样本少时报告原始样本和次数，不给出看似精确的长期可靠性结论。

## 9. 分阶段实施与验收

| 阶段 | 工作与交付 | 完成条件 |
|---|---|---|
| A：先修基础 | 严格配置校验；修正说明；独立用户配置；安装备份；核实模型目录与委托工具差异 | 本轮复现的无效配置均被明确拒绝；更新保留配置；明确可用、不可用、未知的委托目标 |
| B：模型池 | schema v2、profiles/roles/tasks、参数与上下文筛选、选择解释、v1 迁移 | 选择结果可重复；无候选明确失败；换模型只改 profile；老配置可迁移并保留备份 |
| C：可靠委托 | worker 协议、任务状态、预算、失败记录、冷却、检查部分产物后续做 | 超时无重复写入；总预算不能绕过；冷却和恢复可验证；不会错误地把质量失败判为服务故障 |
| D：小范围真实试用 | 按角色各选 1 个主候选和 1 个备选，运行代表性任务，再决定扩容 | 留存真实调用、产物和验收证据；新模型逐个通过后启用；得到可比较的延迟与质量数据 |

建议把 A、B 作为 v0.4 的范围，把 C、D 作为后续可用性版本。若阶段 A 证实当前运行时无法委托目标 GLM，先完成兼容性解决；不以未验证候选的配置完成代替实际接入。

### 必须覆盖的测试

| 测试组 | 场景 | 验收证据 |
|---|---|---|
| 配置 | 错误类型、缺字段、空池、未知引用、自指重复、参数冲突、旧版本迁移 | 明确错误码/字段路径，无隐式错误路由，迁移前有备份 |
| 选择 | 已禁用模型、工具不支持、推理参数不兼容、上下文不足、全部冷却 | 只选兼容模型，逐项说明跳过原因，无候选时停止 |
| 语义 | 纯讨论、纯读代码、纯编辑、先讨论再改、只讨论不改、继续原任务 | 遵守角色和读写范围，保留原约束，不增加用户未授权的工作 |
| 委托 | worker 继承 skill、超时仍运行、部分修改后失败、会话重启 | 检测并限制额外委托，无双写，按已有产物续做 |
| 故障 | 429 与恢复时间、503 暂时故障、401、无效模型、明确额度耗尽、全部候选失败 | 有界重试、正确故障作用域、冷却后受控恢复、无无限兜底 |
| 安装 | 全新安装、有个人配置的升级、同版本重装、源包损坏、Codex 安装失败、有其他插件 | 用户配置和其他插件保留；失败后能恢复；所测源码与安装版本对应 |
| 实际模型 | 每个入池模型的委托、必要工具调用、读代码；编码角色另测修改和验证 | 有工具调用记录、真实文件产物和验收结果，不能只凭固定字符串回复判定通过 |

先用临时目录和假 agent 结果验证确定性的状态及选择逻辑，再开展有限的真实模型测试。模拟测试不作为真实 503 恢复成功的证明；真实调用测试也不代表覆盖所有故障场景。

## 10. 实施时的默认选择

保持 GLM 优先调度和编码、GPT 优先讨论的用户偏好；模型排序以有限试用数据修正。首版使用静态优先级、一个活动写入 worker、最深一层委托和有界重试。

需要通过检查和试验补齐的信息包括：当前会话实际主模型、GLM 及新 GPT 的委托支持、各候选的工具和参数兼容性、供应商真实错误格式、别名/额度组关系、子 agent 文件共享行为。查不到的项目保留未知，不填入猜测。

验收目标是能清楚回答：为什么选这个模型、实际调用是否成功、失败后发生了什么、有没有重复修改、更新是否保留配置。自动按余额评分、更广泛的并行编排和主模型代理恢复留待这些基础路径验证后再考虑。
